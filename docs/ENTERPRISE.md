# 개인 도구에서 조직으로: 무엇이 바뀌어야 하나

이 프로젝트는 대학생 한 명의 한 주(eCampus, 팀플, 인턴 준비)를 위한 개인용 업무 에이전트입니다. 같은 구조를 조직에 들이려면 무엇이 필요한지, 지금 있는 것과 없는 것을 나눠 적습니다. 조직 도입의 핵심 질문은 결국 **"누가, 어떤 데이터에, 어떤 근거로 접근했고, 무엇이 모델로 나갔는가"**입니다.

## 지금 있는 것

| 영역 | 현재 구현 | 위치 |
| --- | --- | --- |
| 접근 경로 단일화 | 정책 게이트웨이: MCP 클라이언트(에이전트, Claude Code, Claude Desktop)는 게이트웨이 하나에만 붙고, 게이트웨이가 GitHub·Gmail·Calendar·eCampus 서버에 붙음 | `mcp-servers/gateway` |
| 도구 단위 허용 | 허용 목록 밖 도구는 `tools/list`에서 빠지고, 이름으로 호출해도 `tools/call`에서 거절 | gateway, `runAgent` |
| 행 단위 제외 | 제외 규칙(보낸 사람·제목·미리보기 부분 일치)에 걸린 항목은 모델·리포트로 가지 않음 | `excludedBy` |
| 민감정보 | 메일 주소, 전화번호, 학번, 주민등록번호, 계좌번호, 카드번호(Luhn 검사)를 가리고 종류별로 셈 | `maskPii` |
| 감사 | 호출마다 한 줄, 클라이언트 이름(MCP `initialize`), 인자, 행 수, 가린 개수. SHA-256 해시 체인이라 수정·삭제·순서 변경을 검증으로 알 수 있음 | gateway `--audit`, 웹 감사 로그, `npm run audit:verify` |
| 지시문 방어 | 메일·이슈 속 지시문을 감지해 표시하고 데이터로만 다룸, 쓰기 도구 없음, 출처 검증 | `detectInjection`, `generateReport` |
| 읽기 전용 | 모든 MCP 도구가 `readOnlyHint` | 각 서버 |
| 사용자별 접속 | 게이트웨이 원격 모드(Streamable HTTP): 사용자별 Bearer 토큰(해시만 저장), 세션은 사용자에 묶이고, 사용자 정책은 게이트웨이 정책보다 엄격하게만, 감사 행마다 사용자 | `mcp-servers/gateway --http --users` |
| 서버 소유 정책 | API는 `POLICY_PATH`의 정책이 기준이고, 요청은 더 엄격하게만 바꿀 수 있음(풀려고 하면 403) | `tightenPolicy` |
| 이름 가명 처리 | 메일 보낸 사람 이름을 모델에는 사람A·사람B로 보내고, 리포트에서는 원래 이름으로 복원 | `Pseudonymizer` |

## 조직에 필요한데 아직 없는 것

1. **신원과 역할(RBAC/ABAC)**
   - 지금 신원은 게이트웨이가 발급한 사용자별 토큰입니다. 로컬 연결(stdio)에서는 MCP 클라이언트 이름뿐이라 위조할 수 있습니다.
   - 조직에서는 SSO(OIDC/SAML)로 사용자를 확인하고, 게이트웨이 정책을 사람·그룹·역할 단위로 정해야 합니다. 예: "채용팀만 `gmail__search_emails` 허용"
   - 감사 행에는 클라이언트 대신 사용자 ID가 남아야 합니다.
2. **정책의 수명주기**
   - 지금 정책은 브라우저(웹)나 JSON 파일(게이트웨이)에 있습니다.
   - 필요한 것: 중앙 저장소, 변경 이력(누가, 언제, 무엇을 바꿨는지 — 이것도 감사 대상), 승인 후 배포, 정책 버전을 감사 행에 기록하기.
3. **승인 흐름(쓰기 작업)**
   - 이 프로젝트는 읽기 전용이라 이 문제를 피했습니다.
   - 메일 발송이나 이슈 수정 같은 쓰기 도구가 들어오면, 위험 등급별로 "사람이 승인해야 실행" 단계를 게이트웨이에 둬야 합니다.
   - 요청, 승인, 실행이 같은 해시 체인에 남아야 합니다.
4. **감사 로그의 보관과 외부 고정**
   - 해시 체인은 로그 *안에서* 바뀐 것을 드러내지만, 파일 전체를 새로 쓰면 막지 못합니다.
   - 주기적으로 체인 머리(head) 해시를 외부(WORM 스토리지, 별도 시스템)에 고정하고, 보관 기간과 접근 권한, SIEM 연동을 둬야 합니다.
5. **민감정보 탐지의 한계**
   - 정규식은 형식이 정해진 식별자만 잡습니다. 이름, 주소, 진료·성적 같은 맥락적 민감정보는 못 잡습니다.
   - 조직에서는 사전과 분류 모델을 함께 쓰는 DLP 엔진, 탐지 근거 보존, 오탐·미탐 피드백 루프가 필요합니다.
   - 문서 첨부(PDF, 이미지)도 대상입니다.
6. **모델로 나가는 경로 통제**
   - 지금은 마스킹 후 원하는 LLM 제공자로 바로 보냅니다.
   - 조직에서는 승인된 모델과 리전만 허용하고, 데이터 보존 계약(제로 리텐션)을 확인하고, 사용량·비용을 부서별로 집계해야 합니다.
7. **자격 증명**
   - 지금은 OAuth 토큰을 서버 메모리나 암호화 파일에 둡니다.
   - 조직에서는 KMS·Vault로 관리하고, 서비스 계정은 최소 권한으로, 토큰 교체와 회수를 감사에 남겨야 합니다.

## 배포 그림 (조직)

```
사용자(SSO) ─▶ AI 클라이언트 (사내 에이전트 · Claude Desktop · Claude Code)
                 │  MCP
                 ▼
          정책 게이트웨이  ──▶ 정책 저장소(버전·승인)
          · 사용자/역할별 허용 도구        ──▶ 감사 저장소(해시 체인 + 외부 고정)
          · 행 제외 · DLP 마스킹
          · 쓰기 도구 승인 흐름
                 │  MCP
                 ▼
     GitHub · Google Workspace · LMS · DB · 사내 시스템 MCP 서버
```

이 저장소의 게이트웨이는 이 그림의 가운데 상자를 사용자 1명 규모로 구현한 것입니다. 그래서 위 1~7번이 그대로 다음 작업 목록이 됩니다.
